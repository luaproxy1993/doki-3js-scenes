# 手法摘要

这里写的是读过源码或在线包之后的归纳，不是着色器抄本。涉及《溪间四时》的部分，请对照 [annac777/xi4u](https://github.com/annac777/xi4u) 的路径阅读原文，并保留 MIT 许可与 AC 的署名。不要把该仓库的源文件、资源或大段原文粘进 Doki 项目。

THE GROWING VALLEY 没有公开仓库，下列观察来自已加载的 https://growing-valley-portfolio.fyshark.workers.dev 脚本结构，只借模式。

## 1. 先写死三条体验约束

《溪间四时》的 [REPLICATION_GUIDE.md](https://github.com/annac777/xi4u/blob/main/REPLICATION_GUIDE.md) 把不可变目标写在最前面：手机优先的竖向插画构图；每个物体在三维里要有可信支撑；时间、季节、天气、动物和声音共用一条可暂停的时间线。Doki 地点也可以先写三句类似的约束，再开工。构图未稳时不要先做几千片叶子。

模块切分见该指南第 2 节，以及仓库 `app/`：`world.ts` 装配与循环，时钟、地形、树、季节生命、后期各管一块。页面只有全屏 Canvas 加一层无底板 UI（`app/page.tsx`）。

## 2. 一条时间线：时辰、日夜、四季、天气

关键文件：

- `app/garden-clock.ts`：确定性时钟，不依赖 `Date` 或 Three.js。一天 360 秒，一季 720 秒，四季 48 分钟。艺术化纬度约 35°、赤纬幅度 20°、晨昏带宽 12°，不是某地某日的星历。太阳与月亮方向近乎相对；夜间混合按太阳高度平滑插值。
- `app/weather-cycle.ts`：天气只有晴、雨、雪。按季节和昼夜给降水概率（春天偏雨、冬夜偏雪），自动抽取间隔 60–120 秒；手动选择会保持 120 秒。暂停和切到后台的时间不计入等待。
- `app/daylight-transition.ts`：点日夜按钮时，约 4 秒走完日出或日落，不在地平线处切整幅快照。
- `app/scene-transition.ts`：季节、画风或拖动时辰时，用一层冻结的 2D 覆盖做短淡化；UI 不参与淡化。
- `app/celestial-bodies.ts`：远景太阳与镂空弯月，按屏幕 CSS 像素定大小，避免正交相机下缩成一个点。
- `app/day-night-life.ts` 与 `app/seasonal-life.ts`：摆件用季节 / 昼夜显隐表，而不是一堆互不相认的开关。夏夜关门不只是换模型，还要挡住室内光线外溢。
- `app/garden-theme.ts`：页面背景与强调色随季节和昼夜改变。

实操要点：

- 日光与月光各用一个方向光。地平线附近先收掉旧光，再抬新光。月光可以只做冷色照明和水面反光，**不要**再投一套实体阴影，否则晨昏会出现方向相反的双影。这一点在 `DESIGN_REQUIREMENTS.md` 与 README 里写得很明确。
- 季节不是四套场景，而是同一套几何上的材质、事件和显隐。下雨、下雪要受季节约束：溪间四时里春夏秋不下雪，冬天不下雨。
- 隐藏标签页后不要把积压的 elapsed time 一次灌进模拟，造成时间跳跃。
- THE GROWING VALLEY 把季节做成一组按钮（spring / summer / autumn / winter），另有日夜开关；季节在界面里叫 weather。分区和昼夜是同一份前端状态，而不是各写各的。

## 3. 等轴测玩具世界与像素后期

《溪间四时》用正交相机，但「等轴测」不等于某个固定夹角。取景在 `app/portrait-framing.ts`：收集持久几何（含实例变换）的包围点，按相机的右 / 上轴投影后适配竖屏、横屏和桌面，而不是拿一个带大量虚空的轴对齐盒子去套。

后期在 `app/pixel-renderer.ts`，画风开关在 `app/render-style.ts`（像素格默认 2 个 CSS 像素）。合成顺序大致是：

1. **像素采样。** 像素模式把场景画到约 `CSS 尺寸 / 像素格` 的目标上，再用最近邻放大。像素格是屏幕空间的采样单位，不要和 renderer 的 DPR 乘两次。`image-rendering: pixelated` 只影响缩放，不会单独把全分辨率画面变成像素风。
2. **墨线。** 自定义 `GardenInkPass` 根据深度和法线不连续勾边，不勾纹理上的颜色变化。细草、透明光效、水面高光应设 `userData.inkOutline = false`，否则画面会脏。原生模式约一个 CSS 像素线宽，像素模式约一个采样格。README 写明参考过 Three.js 的 `RenderPixelatedPass` 与 `OutlinePass`，但最终是自定义合成。
3. **色阶与抖动（像素模式）。** 全屏 palette pass 做有限色阶，并加轻微的 Bayer 抖动；原生模式绕过这一级。抖动不应当成会闪的噪声铺满所有表面。
4. **夜景微光。** 仅对真正发光的表面做高阈值、少量采样的 glow，而不是把整幅夜景提亮。
5. **抗锯齿。** 原生模式有谨慎处理过混合的 FXAA；像素模式保持最近邻边缘。

UI 必须留在后期之外，文字才能保持清晰。粒子在像素模式下要有最小可见尺寸（雪、萤火虫至少占一个格），雨线宽度按屏幕像素来写，不要假定线图元在所有设备上遵守设定宽度。雨的实现见 `app/rain-streaks.ts`。

## 4. 程序化模型，还是 DCC 资产

溪间四时的需求写明：建筑、植物、角色、动物、纹理、天气和水面都由代码生成，运行时不依赖外部图片、模型、HDR 或网络接口。THE GROWING VALLEY 的打包脚本里未见 `GLTFLoader` / `useGLTF` / `.glb`，与作者「模型多为代码生成」的说法一致。

适合代码搭的部分：

- 地面与河岸：用中心曲线和稀疏控制点，而不是厚方盒。见 `app/terrain-footprint.ts`。
- 树：Catmull–Rom 曲线加环形截面，半径连续收窄，末端加偏转，冬天没叶子时也不会露出平切面。树冠沿枝条分层实例化叶片，并留天光缝。见 `app/ancient-tree.ts`、`app/tree-profile.ts`。落叶要从当季仍可见的叶实例出发，见 `app/canopy-fall.ts`。
- 草：根部固定的分段弯叶，随共享阵风弯曲，不要成排的竖直尖刺。见 `app/curved-grass.ts`。
- 水与冰：水面、流光、薄冰和积雪都贴着真实岸线或瓦面，而不是悬浮一层。见 `app/water-surface.ts`、`app/water-current.ts`、`app/winter-creek-ice.ts`、`app/snow-accumulation.ts`、`app/snow-surface.ts`。积雪有上限；檐口落雪用对象池（少量复用），不必上完整物理引擎。
- 动物与人物：父子骨架，头颈始终连着身体；路径先检查落脚面。见 `app/seasonal-fauna.ts`、`app/spring-cat.ts`、`app/summer-sleeper.ts`。

何时才上 Blender / glTF：主体已经有明确比例，或需要无法用代码诚实完成的雕塑、服装、机械。生成式 3D（如 Dilum 作品提到的 Hunyuan3D / World Labs）可以当素材来源，但交互状态、碰撞和灯光仍要在场景里设计。不要为了「像作品集」先塞一批互不统调的资产。

## 5. 可探索低模地图

从 THE GROWING VALLEY 可借用的结构（不要借用它的山谷外形和文案）：

- 世界分成少量命名分区，地面路标与侧栏说明是同一套 id。
- 有总览状态，也有点选后的焦点；相机可以用轨道控制，不必一上来就做第一人称。
- 季节和日夜是全局 store，植物和天空读同一份状态。
- 重复植被用 `InstancedMesh`。R3F 的 `Canvas` 只包 3D，外壳（标题、季节按钮、联系面板）走普通 React DOM。

这和溪间四时的「可旋转微缩景观」是两条路：一个是围绕一座庭院慢慢看，一个是在一张小地图上改换分区。选一个作为主体验。

## 6. 地理沙盘：底图与太阳位置

「腾讯企鹅岛」笔记的模式：OSM + 卫星底图，太阳按深圳纬度和经度计算，单文件 HTML。站点未公开，下面只记原则。

- 太阳方向要用地点纬度和场景日期 / 时辰来算，不要只旋转一个装饰用的光球。若只要气氛而不是真太阳，像溪间四时那样写明「艺术化轨迹」，不要假装是天文模拟。
- 底图是贴地的参考，不是场景的全部细节。建筑和阴影仍要自己做。
- 地图供应商的 token、密钥和配额属于宿主或本地代理，不能写进 `doki.pack` 前端。
- 单文件好分发，但 dense 网格和卫星纹理很容易卡。先限制视野和阴影图尺寸，再加建筑密度。作者已说明该沙盘仍然较卡。

## 7. 风格化草地与密集实例的性能

草地是典型的 etude，也是性能陷阱。

- 溪间四时用少量共享的弯叶网格，固定根部，用阵风而不是每片草一个位移着色器（`app/curved-grass.ts` 的注释写明了这一点）。树叶、落叶、风铃读同一阵风信号，见 `app/garden-atmosphere.ts` 的 `gardenWind`。
- 上游 `skills/threejs-reference-diorama/references/rendering.md` 建议：重复的叶、草、瓦用实例；动画里复用临时向量和矩阵；透明层和阴影图要封顶；切换季节时要回收几何、贴图和监听，不能越切越涨。
- 若参考「Grass Paint」这类作品，先分清哪些是纯 shader、哪些依赖美术贴图。可调密度和风速是优点；把别人的贴图带进 Doki 包则不是。
- 像素模式下，细草地不要再叠加墨线。正交相机里过小的粒子会小于一个像素，需要按屏幕尺寸保底。

通用的 draw call、实例化和填充率问题，转到 `threejs-performance`。

## 8. R3F 还是 vanilla Three.js

两种都可以做出上面的配方，选择看项目已有栈，而不是潮流。

- **vanilla + 薄 UI**（溪间四时）：`createWorld(host)` 管场景，React 只画控制条。适合高度自定义的后期通道、离线单文件打包、以及要精确控制渲染顺序的像素风。时钟模块甚至可以完全不引用 Three。
- **R3F**（THE GROWING VALLEY）：`@react-three/fiber` 的 `Canvas` 管 3D，分区 UI 仍在 DOM。适合本来就是 React 站点、状态和界面已经在 React 里的作品集或 Doki 前端壳。

不要在同一个地点里混两套生命周期。不管选哪条，场景代码都要和控件、后期分开。R3F 的具体 hook 与颜色空间，走 `threejs-react-three-fiber` 和 `threejs-fundamentals`。

## 9. 气氛类配方的补充

- **电影感驾驶：** 可玩参考是 Anderson Mancini 与 Sunag 的 Threejs-Punk Drive（WebGPU + TSL）。学的是雨、灯、湿路和跟随镜头，而不是复制那座赛博城市。若目标运行时是 WebGL 而不是 WebGPU，要提前改预期，不要把 TSL 节点当普通 ShaderMaterial 用。
- **超现实走廊：** 倒置、线框、悬浮代码板都可以当布景。先规定重力、上下和可走边界，再夸张。红色线框不要变成默认的 debug overlay。
- **产品可视化：** 交互要能说明一个过程（包怎么走、细胞怎么分层、货怎么流转）。生成式贴图可以做表面，但不能替代可读的状态。

## 10. 验收时看什么

编译通过、类型检查通过，只说明构建过。视觉上至少抽查：

- 主视角的剪影、重叠和留白是否还是当初那句话里的气质
- 旋转后是否仍有支撑和连续几何，而不是只在正面成立
- 日夜扫过晨昏时，阴影方向和强度有没有跳变或双影
- 季节切换时，禁止的天气有没有残留；反复切换后 GPU 资源有没有只增不减
- 像素 / 原生（若做了）在 DPR 1 和 2 下格子大小是否正确，文字是否仍清晰
- 手机竖屏、短横屏、桌面的控件是否都能点到
- 包内有没有密钥、绝对 CDN、或误打入的参考图

溪间四时自己的验收想法见上游 `skills/threejs-reference-diorama/references/acceptance.md`。Doki 出包前仍要走 `/doki-game-maker` 的导出剔除规则和 `/world-ship-qa`。
